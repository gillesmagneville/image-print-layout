# M0a report — the rendering engine (librsvg + cairo)

🇫🇷 [Version française](M0.fr.md)

This report covers the first part of milestone M0 ("truth prototype", `ARCHITECTURE.md`
§14): the minimal chain **Go → cgo → librsvg → cairo → PDF**, tried on a synthetic SVG
and on the real Mini-CAD. The second part, **M0b**, has started (see "M0b, first results"
below): the engine builds and passes its self-test under Windows; the GTK4 window
(gotk4) remains to be done.

Measurements made with librsvg 2.58.0 and cairo 1.18.0 (Ubuntu 24.04), poppler 24.02 to reread
the PDFs, Go 1.24. The repository does not contain the real Mini-CAD (it describes a real
infrastructure): the tests take it if they find its path in `SVGPL_MINICAD`, and the
`internal/testsvg` generator provides a public equivalent of the same dimensions.

## Verdict

**The engine is retained: the bet of decision 5 is won.** A design flaw was
found and fixed along the way (discovery 1); it does not call the choice into question.

| M0 exit criterion | Result |
| --- | --- |
| 4 pages of 595.28 × 841.89 pt | Yes, reread with `pdfinfo` (tolerance 0.02 mm), on the synthetic SVG and the Mini-CAD |
| Drawing width of 200 mm on each page | Yes: the clip width read in the PDF is 566.93 pt (200 mm) on all four pages |
| Seam test passed | Yes, by two complementary checks (discovery 6) |
| Two exports with the same SHA-256 | Yes, three exports (one of them after reloading the document, a second apart): `d72706b2d5d3064c` for the synthetic one, `a87fdfcc07f97803` for the Mini-CAD |
| PDF size not multiplied by the number of pages | Yes: 4 pages = 1.08 times the whole drawing on a single page (Mini-CAD), 1.15 times (synthetic) |
| Windows build that produces the same plan | **Not done**: the engine builds and passes its self-test under Windows, but the 4-page plan is not yet produced there nor compared (M0b) |

## Measurements

The Mini-CAD: 1,280 × 5,479 units, 157,394 bytes, produced by Inkscape 1.4.3. It contains
459 `text` elements (198 `tspan`), 121 `rect`, 55 `path`, 36 groups, 36 marker usages,
23 `stroke-dasharray`, 27 transformations and 2 mentions of opacity. It contains no image, no
filter, no `clip-path`, no mask, no gradient. It requires the IBM Plex Sans and IBM Plex
Mono fonts, with fallback fonts.

| Measurement | Value |
| --- | --- |
| Loading the Mini-CAD | 13 ms |
| Export of 4 A4 pages (acceptance scenario: cuts 1,380.5 / 2,760 / 4,120.25) | 0.9 to 1.4 s (the first time, the font cache counts) |
| Export of the whole drawing on a single tall page | 0.23 to 0.27 s |
| Rendering a 640 × 700 pixel window | 0.24 to 0.41 s |
| 4-page PDF / one-tall-page PDF | 77,080 bytes / 71,695 bytes |
| Box measurement (`Measure`) | 36 groups in 0.68 s (19 ms each), 121 `rect` in 4 ms, 459 `text` in 0.35 s (0.8 ms each) |
| Boxes outside the document | None; 3 paths are measured empty |
| Fonts in the PDF | 7 embedded TrueType subsets (IBM Plex Sans, Sans SemiBold, Mono, Mono Medium, Mono SemiBold), selectable text, accents included |
| Difference with Chromium (rendering of the same SVG, 96 dpi) | Mean difference of one gray level out of 255; 0.2% of the 16 × 16 pixel squares differ by more than 24 levels, none by more than 48 |

The time of an export grows with the number of pages: each page redraws the document, and
cairo only writes the operations that touch the clip. A window rendering takes a time of the
same order as that of a whole page, which suggests that its cost depends on the document
more than on the window: the preview (M2) will have to cache tiles. Peak memory
was not measured.

## Discoveries that change the design

1. **A recording surface is not suitable.** The initial plan drew the document once in a cairo
   recording surface, then painted it on each page. With cairo
   1.18, the PDF then writes only **a single object** whose extent is that of its first
   use: pages 2 to 4 came out **empty**, and the text became outlines. The engine therefore
   draws the document **directly on each page**, under a rectangular clip: the
   text stays text, the fonts are embedded, the file does not grow (measurements
   above), and the clip is a vector `re W n` in the PDF. The first seam test
   had nevertheless passed on these empty pages, because its tolerance let white
   through in place of gray: it is rewritten, and a test checks that it fails when a page is
   shifted.
2. **`rsvg_handle_get_geometry_for_layer`, not `_for_element`.** To measure an element in
   the document's coordinate system, the "layer" variant is the right one; "element" gives
   coordinates relative to the element.
3. **Resolution to set explicitly.** librsvg converts physical lengths (`mm`,
   `in`, `pt`) with its own default resolution (90 dpi). The engine imposes 96, like SVG
   and CSS, and `units` makes the same assumption.
4. **Clip and path coordinates in 24.8 fixed point.** cairo rounds to 1/256 of a point
   (0.0014 mm) the clips and paths it writes. The position of a cut in the PDF is
   therefore exact to within 0.0014 mm, under the 0.005 mm tolerance of `ARCHITECTURE.md` §5, but not
   to the float.
5. **Dates and determinism.** cairo writes the creation and modification dates: the engine
   fixes them (2000-01-01T00:00:00Z). With that, the same document gives the same file. The
   PDF "producer" field contains the cairo version: byte equality only holds for equal
   versions, as `ARCHITECTURE.md` §11 already says.
6. **A rasterizer does not redraw the same image identically to the pixel.** Comparing
   pixel by pixel the cut PDF and the PDF of the whole drawing found 0.06% of pixels different:
   98% on the text (poppler places the glyphs on a quarter-pixel grid), the rest
   on an edge falling exactly at mid-pixel; on the Mini-CAD, thin lines that poppler snaps to
   the pixel grid and that a hundredth-of-a-pixel difference makes change row, hence
   whole rows of 76 to 93% different pixels. These were not defects of the PDF.
   The seam test therefore combines two checks:
   - **the geometry written in the PDF**, reread in the content stream (Flate decompression
     with the standard library, no PDF library): clip rectangle and offset of the
     drawing of each page, compared with the plan, exact to 1/256 of a point; it sees a shift
     of 0.1 unit, and holds for any cut position;
   - **the pixels, by squares** of 16 × 16 pixels whose gray average is compared (tolerated
     difference: 24 levels; maximum measured difference: 14), at 254 dpi on cuts that fall
     on the pixel grid and at 150 dpi on the cuts of the acceptance scenario. This
     check sees content that is lost, repeated or moved (it detects a shift of 12 units,
     i.e. 1.9 mm) but not a line shifted by one pixel.
7. **A missing font is replaced without a word.** Without IBM Plex, librsvg picks
   other fonts (here DejaVu) and the PDF embeds them: nothing indicates the change. The
   detection planned in §12 of `ARCHITECTURE.md` is therefore indispensable: list the families
   requested by the document, resolve them through fontconfig and flag each replacement
   before the export. A font resolution in `engine` is to be planned in M2.
8. **The factor between `viewBox` units and intrinsic pixels is not tested.** The engine
   works in intrinsic pixels at 96 dpi; the Mini-CAD is one to one. For a document
   whose `width`/`height` differ from the dimensions of the `viewBox`, `svgdoc` will have to compute this
   factor, and a test will have to establish it.

## What M0a does not validate

- **GTK4**: the gotk4 build under Windows (MSYS2 UCRT64): that is M0b. The engine, for its part, builds
  under Windows and is bundled with its libraries (see below).
- **Rasterized elements**: the Mini-CAD has no filter, the fallback resolution remains to be
  measured on a file that contains some.
- **Fidelity**: compared with Chromium and not with Inkscape, which is not installed here. On the
  Mini-CAD, the two renderings agree; a comparison with Inkscape remains desirable.
- **Other versions**: librsvg is older on Ubuntu 22.04. Only 2.58.0 is tried.
- **Heavy documents**: the 100,000-element test is not done.
- **Other machines**: determinism is established on one machine; equality between machines
  is not promised (`ARCHITECTURE.md` §11).
- **`flowRoot`, `@font-face`, `foreignObject`**: still to be confirmed (`ARCHITECTURE.md` §12).

## M0b, first results: the engine under Windows

The build of the engine under Windows (MSYS2 UCRT64, Go and cgo) is done by
`windows/build-windows.sh` and tried by the CI on `windows-latest`
(see `windows/README.md`). What this first trial established, with librsvg 2.63.2,
cairo 1.18.6 and GLib 2.90 (the MSYS2 versions that day, newer than those
of Ubuntu 24.04):

- **The same program passes `-selftest` under Windows**: loading, measurement, rendering to an image,
  embedded PNG image, PDF export with embedded font and two identical exports, with only the
  Windows PATH, from the build folder, from a portable version
  unzipped elsewhere and from an installation folder. The delivered folder is therefore
  relocatable: 43 DLLs, the fontconfig configuration and the image loaders are enough.
- **The libraries must be told where their configuration is.** Fontconfig and gdk-pixbuf do
  not know where to look when the program is not installed under a fixed prefix;
  `engine.ConfigureRuntime` points them to the data delivered next to the program, through
  environment variables set with `_putenv_s` (the one of `os.Setenv` does not touch the copy
  of the environment that C reads). The cache of the image loaders carries paths relative
  to the prefix.
- **Variables exported by a DLL cannot be read through cgo.** `rsvg_major_version` and its
  neighbors returned unrelated numbers (`1257383423.…`): cgo reads the entry point
  of the DLL and not the value. They are now read in a C function, and a test checks
  that the versions have the shape of a version.
- **MSYS2's Go does not find its folder again** (it is compiled with `-trimpath`): the script
  sets `GOROOT`.

What remains to be done to close M0b: produce under Windows the 4-page plan of the acceptance
scenario and compare it with the Linux one (through the geometry read in the PDF, not byte by
byte: the cairo versions differ); build gotk4 and a GTK4 window under MSYS2;
try the package on a clean Windows machine, which the CI does not replace.

## Reproducing

```sh
sudo apt-get install librsvg2-dev libfontconfig-dev poppler-utils fonts-ibm-plex
CGO_ENABLED=1 go test -v ./internal/engine ./internal/testsvg

# with the real file (not versioned)
SVGPL_MINICAD=/path/to/Flux-reseau-Mini-CAD.svg CGO_ENABLED=1 go test -v ./internal/engine
```

The tests that read the PDFs skip if a poppler tool is missing, except when the `CI` variable
is set: on continuous integration, a missing tool is an error.
