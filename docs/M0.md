# Rapport M0a — le moteur de rendu (librsvg + cairo)

Ce rapport rend compte du premier volet du jalon M0 (« prototype de vérité », `ARCHITECTURE.md`
§14) : la chaîne minimale **Go → cgo → librsvg → cairo → PDF**, essayée sur un SVG synthétique
et sur le vrai Mini-CAD. Le second volet, **M0b**, est entamé (voir « M0b, premiers résultats »
plus bas) : le moteur se construit et passe son auto-test sous Windows ; la fenêtre GTK4
(gotk4) reste à faire.

Mesures faites avec librsvg 2.58.0 et cairo 1.18.0 (Ubuntu 24.04), poppler 24.02 pour relire
les PDF, Go 1.24. Le dépôt ne contient pas le Mini-CAD réel (il décrit une infrastructure
réelle) : les tests le prennent s'ils trouvent son chemin dans `SVGPL_MINICAD`, et le
générateur `internal/testsvg` fournit un équivalent public de mêmes dimensions.

## Verdict

**Le moteur est retenu : le pari de la décision 5 est tenu.** Un défaut de conception a été
trouvé et corrigé en chemin (découverte 1) ; il ne remet pas en cause le choix.

| Critère de sortie de M0 | Résultat |
| --- | --- |
| 4 pages de 595,28 × 841,89 pt | Oui, relu avec `pdfinfo` (tolérance 0,02 mm), sur le SVG synthétique et le Mini-CAD |
| Largeur du dessin de 200 mm sur chaque page | Oui : la largeur du clip lue dans le PDF vaut 566,93 pt (200 mm) sur les quatre pages |
| Test de couture réussi | Oui, par deux contrôles complémentaires (découverte 6) |
| Deux exports de même SHA-256 | Oui, trois exports (dont un après rechargement du document, à une seconde d'écart) : `d72706b2d5d3064c` pour le synthétique, `a87fdfcc07f97803` pour le Mini-CAD |
| Taille du PDF non multipliée par le nombre de pages | Oui : 4 pages = 1,08 fois le dessin entier sur une seule page (Mini-CAD), 1,15 fois (synthétique) |
| Build Windows qui produit le même plan | **Pas fait** : le moteur se construit et passe son auto-test sous Windows, mais le plan de 4 pages n'y est pas encore produit ni comparé (M0b) |

## Mesures

Le Mini-CAD : 1 280 × 5 479 unités, 157 394 octets, produit par Inkscape 1.4.3. Il contient
459 éléments `text` (198 `tspan`), 121 `rect`, 55 `path`, 36 groupes, 36 usages de marqueurs,
23 `stroke-dasharray`, 27 transformations et 2 mentions d'opacité. Il ne contient ni image, ni
filtre, ni `clip-path`, ni masque, ni dégradé. Il demande les polices IBM Plex Sans et IBM Plex
Mono, avec des polices de repli.

| Mesure | Valeur |
| --- | --- |
| Chargement du Mini-CAD | 13 ms |
| Export de 4 pages A4 (scénario d'acceptation : coupures 1 380,5 / 2 760 / 4 120,25) | 0,9 à 1,4 s (la première fois, le cache de polices compte) |
| Export du dessin entier sur une seule page haute | 0,23 à 0,27 s |
| Rendu d'une fenêtre de 640 × 700 pixels | 0,24 à 0,41 s |
| PDF de 4 pages / PDF d'une page haute | 77 080 octets / 71 695 octets |
| Mesure des boîtes (`Measure`) | 36 groupes en 0,68 s (19 ms l'un), 121 `rect` en 4 ms, 459 `text` en 0,35 s (0,8 ms l'un) |
| Boîtes hors du document | Aucune ; 3 chemins sont mesurés vides |
| Polices dans le PDF | 7 sous-ensembles TrueType incorporés (IBM Plex Sans, Sans SemiBold, Mono, Mono Medium, Mono SemiBold), texte sélectionnable, accents compris |
| Écart avec Chromium (rendu du même SVG, 96 dpi) | Écart moyen d'un niveau de gris sur 255 ; 0,2 % des carrés de 16 × 16 pixels s'écartent de plus de 24 niveaux, aucun de plus de 48 |

Le temps d'un export croît avec le nombre de pages : chaque page redessine le document, et
cairo n'écrit que les opérations qui touchent le clip. Un rendu de fenêtre prend un temps du
même ordre que celui d'une page entière, ce qui laisse penser que son coût dépend du document
plus que de la fenêtre : l'aperçu (M2) devra mettre les tuiles en cache. La mémoire de pointe
n'a pas été mesurée.

## Découvertes qui changent la conception

1. **Une surface d'enregistrement ne convient pas.** Le plan initial dessinait le document une
   fois dans une surface d'enregistrement cairo, puis la peignait sur chaque page. Avec cairo
   1.18, le PDF n'écrit alors qu'**un seul objet** dont l'étendue est celle de son premier
   usage : les pages 2 à 4 sortaient **vides**, et le texte devenait des contours. Le moteur
   dessine donc le document **directement sur chaque page**, sous un clip rectangulaire : le
   texte reste du texte, les polices sont incorporées, le fichier ne grossit pas (mesures
   ci-dessus), et le clip est un `re W n` vectoriel dans le PDF. Le premier test de couture
   avait pourtant réussi sur ces pages vides, parce que sa tolérance laissait passer du blanc
   à la place du gris : il est réécrit, et un test vérifie qu'il échoue quand une page est
   décalée.
2. **`rsvg_handle_get_geometry_for_layer`, pas `_for_element`.** Pour mesurer un élément dans
   le repère du document, c'est la variante « layer » qui convient ; « element » donne des
   coordonnées relatives à l'élément.
3. **Résolution à régler explicitement.** librsvg convertit les longueurs physiques (`mm`,
   `in`, `pt`) avec sa propre résolution par défaut (90 dpi). Le moteur impose 96, comme SVG
   et CSS, et `units` fait la même hypothèse.
4. **Coordonnées de clip et de chemin en virgule fixe 24.8.** cairo arrondit au 1/256 de point
   (0,0014 mm) les clips et les chemins qu'il écrit. La position d'une coupure dans le PDF est
   donc exacte à 0,0014 mm près, sous la tolérance de 0,005 mm d'`ARCHITECTURE.md` §5, mais pas
   au flottant près.
5. **Dates et déterminisme.** cairo écrit les dates de création et de modification : le moteur
   les fixe (2000-01-01T00:00:00Z). Avec cela, un même document donne un même fichier. Le
   champ « producteur » du PDF contient la version de cairo : l'égalité d'octets ne vaut qu'à
   versions égales, comme `ARCHITECTURE.md` §11 le dit déjà.
6. **Un rastériseur ne redessine pas deux fois la même image au pixel près.** Comparer pixel
   par pixel le PDF découpé et le PDF du dessin entier a relevé 0,06 % de pixels différents :
   98 % sur le texte (poppler place les glyphes sur une grille d'un quart de pixel), le reste
   sur un bord tombant pile à mi-pixel ; sur le Mini-CAD, des traits fins que poppler cale sur
   la grille de pixels et que l'écart d'un centième de pixel fait changer de rangée, d'où des
   rangées entières de 76 à 93 % de pixels différents. Ce n'étaient pas des défauts du PDF.
   Le test de couture combine donc deux contrôles :
   - **la géométrie écrite dans le PDF**, relue dans le flux de contenu (décompression Flate
     avec la bibliothèque standard, aucune bibliothèque PDF) : rectangle de clip et décalage du
     dessin de chaque page, comparés au plan, exacts à 1/256 de point ; il voit un décalage
     de 0,1 unité, et vaut pour toute position de coupure ;
   - **les pixels, par carrés** de 16 × 16 pixels dont on compare la moyenne de gris (écart
     toléré : 24 niveaux ; écart maximal mesuré : 14), à 254 dpi sur des coupures qui tombent
     sur la grille de pixels et à 150 dpi sur les coupures du scénario d'acceptation. Ce
     contrôle voit un contenu perdu, répété ou déplacé (il détecte un décalage de 12 unités,
     soit 1,9 mm) mais pas un trait décalé d'un pixel.
7. **Une police absente est remplacée sans rien dire.** Sans IBM Plex, librsvg choisit
   d'autres polices (ici DejaVu) et le PDF les incorpore : rien n'indique le changement. La
   détection prévue au §12 d'`ARCHITECTURE.md` est donc indispensable : lister les familles
   demandées par le document, les résoudre par fontconfig et signaler chaque remplacement
   avant l'export. Une résolution de police dans `engine` est à prévoir en M2.
8. **Le facteur entre unités du `viewBox` et pixels intrinsèques n'est pas testé.** Le moteur
   travaille en pixels intrinsèques à 96 dpi ; le Mini-CAD est à un pour un. Pour un document
   dont `width`/`height` diffèrent des dimensions du `viewBox`, `svgdoc` devra calculer ce
   facteur, et un test devra l'établir.

## Ce que M0a ne valide pas

- **GTK4** : le build de gotk4 sous Windows (MSYS2 UCRT64) : c'est M0b. Le moteur, lui, se
  construit sous Windows et s'embarque avec ses bibliothèques (voir plus bas).
- **Éléments rastérisés** : le Mini-CAD n'a aucun filtre, la résolution de repli reste à
  mesurer sur un fichier qui en contient.
- **Fidélité** : comparée à Chromium et non à Inkscape, qui n'est pas installé ici. Sur le
  Mini-CAD, les deux rendus concordent ; une comparaison avec Inkscape reste souhaitable.
- **Autres versions** : librsvg est plus ancienne sur Ubuntu 22.04. Seule la 2.58.0 est essayée.
- **Documents lourds** : le test à 100 000 éléments n'est pas fait.
- **Autres machines** : le déterminisme est établi sur une machine ; l'égalité entre machines
  n'est pas promise (`ARCHITECTURE.md` §11).
- **`flowRoot`, `@font-face`, `foreignObject`** : toujours à confirmer (`ARCHITECTURE.md` §12).

## M0b, premiers résultats : le moteur sous Windows

La construction du moteur sous Windows (MSYS2 UCRT64, Go et cgo) est faite par
`windows/build-windows.sh` et essayée par la CI sur `windows-latest`
(voir `windows/README.md`). Ce que ce premier essai a établi, avec librsvg 2.63.2,
cairo 1.18.6 et GLib 2.90 (les versions de MSYS2 ce jour-là, plus récentes que celles
d'Ubuntu 24.04) :

- **Le même programme passe `-selftest` sous Windows** : chargement, mesure, rendu en image,
  image PNG incorporée, export PDF avec police incorporée et deux exports identiques, avec le
  seul PATH de Windows, depuis le dossier de construction, depuis une version portable
  décompressée ailleurs et depuis un dossier d'installation. Le dossier livré est donc
  relocalisable : 43 DLL, la configuration de fontconfig et les chargeurs d'images suffisent.
- **Il faut dire aux bibliothèques où est leur configuration.** Fontconfig et gdk-pixbuf ne
  savent pas où chercher quand le programme n'est pas installé sous un préfixe fixe ;
  `engine.ConfigureRuntime` leur indique les données livrées à côté du programme, par des
  variables d'environnement posées avec `_putenv_s` (celui de `os.Setenv` ne touche pas la copie
  de l'environnement que lit le C). Le cache des chargeurs d'images porte des chemins relatifs
  au préfixe.
- **Les variables exportées d'une DLL ne se lisent pas par cgo.** `rsvg_major_version` et ses
  voisines renvoyaient des nombres sans rapport (`1257383423.…`) : cgo lit le point d'entrée
  de la DLL et non la valeur. Elles se lisent maintenant dans une fonction C, et un test vérifie
  que les versions ont la forme d'une version.
- **Le Go de MSYS2 ne retrouve pas son dossier** (il est compilé avec `-trimpath`) : le script
  fixe `GOROOT`.

Ce qui reste à faire pour clore M0b : produire sous Windows le plan de 4 pages du scénario
d'acceptation et le comparer à celui de Linux (par la géométrie lue dans le PDF, pas octet par
octet : les versions de cairo diffèrent) ; construire gotk4 et une fenêtre GTK4 sous MSYS2 ;
essayer le paquet sur une machine Windows propre, que la CI ne remplace pas.

## Reproduire

```sh
sudo apt-get install librsvg2-dev libfontconfig-dev poppler-utils fonts-ibm-plex
CGO_ENABLED=1 go test -v ./internal/engine ./internal/testsvg

# avec le vrai fichier (non versionné)
SVGPL_MINICAD=/chemin/vers/Flux-reseau-Mini-CAD.svg CGO_ENABLED=1 go test -v ./internal/engine
```

Les tests qui lisent les PDF sautent si un outil de poppler manque, sauf quand la variable
`CI` est définie : sur l'intégration continue, un outil absent est une erreur.
